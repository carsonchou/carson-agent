## 0. 🔴 先講三件推翻派工前提的事,不然下面的清單會被誤讀

### (1) TrustMRR 上「一人做得起來」和「證明了有需求」幾乎互斥

12 筆實抓條目,按活躍訂閱數攤開來看是**雙峰**,中間是空的:

| 量級 | 產品(活躍訂閱數) | 一人做得起來? |
|---|---|---|
| 個位數~29 | CarAI(2)、Ecom Nation(10)、Aila(12)、VoiceBrief(15)、wento.ai(29) | ✅ 都可以 |
| **中間帶(影片作者 $16.5K 所在的區間)** | **本次樣本裡一筆都沒有** | — |
| 375~656 | Kibu(375, HIPAA)、1Lookup(656) | ❌ |
| 未揭露訂閱數但 MRR 20 萬鎂以上 | Rezi(2015 年成立,10 年)、GojiberryAI | ❌ |

⇒ **凡是我做得起來的那些,付錢的人是 2~29 個。** 那個分母不是需求訊號,是雜訊
(memory `search-demand-measurement-traps`:confound 三類之一就是「分母太小的雜訊」)。
凡是分母夠大的,不是十年老公司、就是重法規/重資料基建,不是一人冷啟動的可比對象。

**這直接影響選題法本身**:影片說「用 TrustMRR 看別人賺多少反推 idea」,
但 TrustMRR 能給的其實是**「這個品類有人願意掏錢」**,不是**「這個題目已經被驗證」**。
兩者差一個數量級的證據強度。

### (2) TrustMRR 是自願上架的,不是市場普查

驗證機制是創辦人**主動**授權 Stripe / RevenueCat / Superwall / Creem 唯讀 API(來源:https://trustmrr.com/)。
⇒ 數字本身可信(金流商驗過),**但樣本是自選的**:只看得到願意公開營收的人,
而公開營收本身就是一種行銷動作。失敗的、沉默的、賺錢但不想講的,全部不在上面。
**「站上有 6,000 家」不等於「這是市場的樣子」。**

### (3) 🔴 蒐到的三個「先驗證再開發」實例,**沒有一個是零成本零上線的**

| 實例 | 做法 | 碰不碰紅線 |
|---|---|---|
| Buffer(Joel Gascoigne) | 做兩頁 landing page + 發推文,7 週 120 signup,4 天內第一個付費客戶 | **對外發布** |
| Indie Hackers 貼文 | Reddit 廣告 + Reddit 私訊 | **對外發布 + 動錢** |
| DEV.to 貼文 | 一週做完 landing page 發出去看有沒有人理 | **對外發布** |

(三筆都只到搜尋摘要層級,未逐字核對原頁 —— 但做法形狀夠清楚,足以做這個判斷。)

⇒ **這是本份派工最重要的發現,而且它是個壞消息:**
「不上線、不花錢,我怎麼知道它有沒有人要?」這個問題,
在起始授權範圍內**只有一種答案:讀別人的帳本**(第三方已驗證營收、既有工具的安裝/評論數、公開抱怨量)。
而那本帳回答的是「**這個市場裡有錢**」,不是「**我拿得到人**」——
memory `search-demand-measurement-traps` 已經量過這個差距:
**同一個題目、同一個標題、同一頁,可及性差 177 倍。**

所以下面每一個候選的「零成本儀器」欄,都要當成**次級證據**讀。
真正的第一級證據需要開一格紅線(見第 4 節給 Carson 的問句)。

## 1. 候選清單(7 個,依「零成本需求儀器的強度」排序)

排序判準就是派工指定的那一句:**這個東西不上線、不花錢,我怎麼知道它有沒有人要?**
答得越硬的排越前面。⚠️ **排序不等於推薦** —— 排第一的那個需求證據反而最弱,見它自己的欄位。

> 🔴 **通則(2026-09-09 獨立驗證糾正,見第 6 節)**:
> 我原本只對候選 4 套用了「本機免費版做出來的東西,不足以判斷這個產品行不行」這條判準,
> 卻沒對候選 2、3 套同一條 —— 而它們的核心同樣是**打一支付費 LLM API**,和候選 4 打付費 TTS 是同一種依賴。
> repo 現有 OpenRouter 金鑰(memory `llm-provider-openrouter-switch`,DeepSeek V4 flash,**Carson 預付制**),
> 所以那不是「辦新金鑰」,**但它是花錢** —— 預付餘額會少,判準「帳單上看得到」成立。
> ⇒ **凡是核心功能要呼叫 LLM / TTS / 外部資料源的候選,做出「可用版」就已經跨線。**
> 這不代表不能做,代表**要先問**。下面各候選的紅線欄已依此重判。

### 候選 1 — 財經/投資內容的「數字溯源 + 誠信守門」工具

- **痛點**:AI 生成的財經內容會編造統計數字,而作者自己看不到。
- **已驗證證據**:
  - ⚠️ **外部帳本是空的**。TrustMRR 12 筆裡沒有這個品類,沒找到任何一家在做這件事並公開營收。
  - 最接近的旁證:wento.ai(修 AI 生成文字的痕跡)MRR $616 / 29 訂閱,2026-06 成立
    — https://trustmrr.com/startup/wento-ai(頁面時間戳 2026-09-09 00:51)
  - YC RFS Fall 2026 第 11 類 **"Proving You're Human"**:
    "Voice clones and fake video calls are getting cheap and ultra-realistic, and fraud like this is exploding."
    — https://www.ycombinator.com/rfs(**相鄰問題,不是同一個問題**)
- **技術可行性**:**已經有大半**。本 repo 的 YT 產線就有事實庫 + 溯源閘門。
  抽成獨立 web app:**2~3 週**。
- **要碰紅線嗎**:🟡 **核心功能不用,但邊界要切乾淨**。溯源比對是規則 / 查表
  (抽稿裡的數字 → 比對事實庫),**不呼叫 LLM**,所以核心可以零成本重現。
  ⚠️ 但如果 prototype 定位成「外部使用者丟任意文章進來」,抽取步驟要處理任意格式文字,
  實務上很可能要靠 LLM 輔助 —— **那一刻就跨進動錢**。
  ⇒ 做的時候把「規則抽取」和「LLM 抽取」切成兩層,先只做前者。
  **這是全清單唯一一個核心功能真的能零成本做出來的候選。**
- **🔴 零成本儀器**:**這是唯一一個 Carson 手上就有真實痛點量測的候選** ——
  本 repo 量到過捏造率 56%(memory `yt-integrity-fabricated-stats-fix`),而且那是**觀眾罵出來的**,
  不是我猜的。且量化阿森頻道 = 現成的分發管道(唯一一個)。
- **🔴 但必須誠實標註**:「我自己有這個痛」是 **n=1**,那是最弱的需求證據,不是最強的。
  memory `distribution-before-quality` 的教訓正是這一種:自己覺得該修的東西,修了 10 小時 / $194,而沒人看。
  它排第一是因為**儀器最硬**(有真實分發 + 有量到的痛),不是因為市場最大。

### 候選 2 — 中文/台灣市場的 AI 履歷產生器

- **痛點**:求職者寫不出通過 ATS 篩選的履歷。
- **已驗證證據**:Rezi,MRR **$255,295**,免費版 + Pro $29/月 + 買斷 $149
  — https://trustmrr.com/startup/rezi(頁面時間戳 2026-09-08 20:16)
  ⚠️ **2015-05 成立,已營運 10 年**。這個數字證明「品類會賺錢」,**不證明「現在進場來得及」**。
- **技術可行性**:純 web app,**不需要外部「資料源」合約**(這是它和候選 5 / 6 的差別),
  但**核心就是 LLM 生成內容,拿掉 LLM 呼叫它就不是這個產品了**。**1~2 週**出可用版。
  技術風險全清單最低,**成本風險不為零**。
- **要碰紅線嗎**:⚠️ **是,連 prototype 都是**(2026-09-09 獨立驗證糾正,原本誤標為「不用」)。
  用既有 OpenRouter 金鑰不算辦新金鑰,但會花掉預付餘額 = 動錢。
- **零成本儀器**:🟡 中等。可零成本量的:104/Cake 公開職缺數、中文履歷模板的搜尋量、
  現有中文履歷工具的評論數。**但這三樣量的都是「有人在找履歷」,不是「有人會付 $29/月」**
  —— 中間隔著台灣市場的付費意願,而那件事沒有現成帳本可讀。
- ⚠️ **它排第二的理由比看起來弱**(獨立驗證員指出,我同意):第 0 節花整段論證
  「訂閱數 2~29 是雜訊、10 年老公司和大 MRR 都不是一人可比對象」,並把 Rezi 歸進「❌ 做不起來」那桶;
  可是候選 2 又把同一個 Rezi 的 $255,295 當「已驗證證據」端出來,只用一句「來得及嗎」帶過。
  ⇒ 這裡的病和候選 3 方向相反但同源:**候選 3 是分母太小,候選 2 是分母夠大但那個大是十年護城河堆出來的**,
  兩者都不能直接當「我做這題會有人買」的證據。**論證力度前後不一致,這點要對 Carson 講明。**

## 3. GymLog 現況(派工第 3 項)

**結論:它沒有「有沒有使用者」這個訊號 —— 不是使用者是 0,是這個問題在它現在的架構下無法回答。**

| 查什麼 | 結果 |
|---|---|
| 站活著嗎 | ✅ `carsonchou.github.io/gymlog/` HTTP 200(`carsonchou.github.io/` 本身 404) |
| 有分析工具嗎 | ❌ 全檔 grep 無 GA / Plausible / Umami / PostHog / 任何計數器 |
| 有帳號系統嗎 | ❌ **Firebase Auth 根本沒啟用**。使用者身分只是 localStorage 一個隨機字串 |
| 資料讀得到嗎 | ❌ Firestore `rooms` 回 403 PERMISSION_DENIED(規則擋得對) |
| repo 流量 | 近 14 天 views 0 / uniques 0、clones 4 ⚠️ **這量的是 repo 頁面不是 App** |

**正負對照(這是「金鑰是活的、只是 Auth 沒開」這句話站得住的原因)**:
拿有效金鑰打 identitytoolkit 回 `CONFIGURATION_NOT_FOUND`;拿亂造金鑰打回 `API key not valid`
—— 兩者訊息不同,所以金鑰有效。
⚠️ 而 Firestore 那邊**好壞金鑰都回 403**,**那個儀器分辨不出「規則擋我」和「金鑰壞了」**,
單獨拿它下任何結論都不成立(memory `verification-that-cannot-fail`)。

README 寫的安裝路徑是「跑 .bat 開 cloudflared 臨時網址 → 自己 iPhone 加到主畫面」,
**連 GitHub Pages 都沒被當成安裝管道**。

⚠️ **證據強度標註**:「好壞金鑰都回 403」那一半,獨立驗證員重跑過,**成立**。
但「Firebase Auth 沒啟用」那一半**只有我一個人量到**(identitytoolkit 的兩種錯誤訊息不同),
驗證員無法重現 —— 他的 WebFetch 在非 2xx 時丟棄 response body 看不到訊息,
而改用會**真的建立匿名帳號**的寫入端點被分類器擋下(擋得對,那超出唯讀範圍,他沒硬繞)。
⇒ 這句是**單一觀測者、未被獨立重現**。要拿它當承重點之前,請 Carson 自己開 Firebase console 看一眼。

⇒ **它不是這條線的分發樣本,它是 `distribution-before-quality` 的又一個實例**:
一個能跑的產品掛在公網上兩個月,而系統結構上不會產生任何一個「有沒有人用」的訊號。
