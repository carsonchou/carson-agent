## 🔴 2026-09-08 重看分母:數字沒錯,但**它結構上只能往下、不能往上**

### 證據鏈(全部實測,非讀碼推論)

```
remaining()        = effective_limit() − spent                    (quota_meter.py:651)
ENFORCE(.env:38=1) → units > remaining() 就 raise                 (:792 / :832)
                   ⇒ spent ≤ effective_limit()  每一天
effective_limit()  = max(ceil, floor_since)                       (:579-583)
  floor_since      = 撞牆日(含)之後成功花到的最高值 ⇒ ≤ effective_limit()
  ceil             = 最近一個撞牆日當天的 spent      ⇒ ≤ effective_limit()
⇒ effective_limit() **永遠不可能升高**;只能降(出現較低的新牆、或帳本被裁)。
```

`_scan()` 現值:`(floor 26001, ceil 26001, floor_since 26001, ceil_day 2026-08-31, since_day 2026-08-31)`
—— **三個值全部取自同一天**。這個分母的 n = 1。

### 這正是 `effective_limit()` 自己寫著要防的那件事,而防不到

它的 docstring 明說修法是為提額寫的:

> 發作條件是提額核准之後 —— 某天成功花超舊牆但沒撞到新牆,floor 升而 ceil 不動
> …所以 floor 只採撞牆日(含)之後的:**提額跟得上、降額也跟得下**

「跟得上」的前提是「**某天成功花超舊牆**」。ENFORCE=1 讓那天不可能發生。
⇒ **這個修法在產線實際組態下是空砲。** 降額跟得下(較低的新牆會拉低 ceil),升額跟不上。

### 最直覺的那根桿子沒有接上(活體實驗)

把 `YT_QUOTA_LIMIT` 從 19,645 調到 50,000 → `effective_limit()` **紋風不動 26,001**。
`if ceil: return max(ceil, floor_since or 0)` 在 ceil 存在時**完全不看設定值**。
⇒ 提額核准後改環境變數**不會有任何效果**,而且不會有錯誤訊號。

1. **讀取幾乎免費**(1 unit),`videos.list(part=status)` 批次 50 個 id **一次呼叫 = 1 unit**。
   所以「確認 34 支現在是否還公開」的成本是 **1 unit**,不是我先前寫的 2~3。
2. **`search.get` 是 100** —— 讀取裡的異類,比其他讀取貴 100 倍。任何「搜尋看看排名」的想法要先看這格。
3. **Analytics 在這張表裡一筆都沒有** —— `youtubeAnalytics.reports.query` 走**另一個配額池**,
   不吃這 26,001。所以「逐支取 estimatedMinutesWatched」對本文件的飽和問題**零影響**。
   ⚠️ 反過來說:**Analytics 有它自己的上限**,只是不在這本帳裡,別以為它無限。

## 三件可以做的,成本與可逆性都不同

1. **提額申請**(最根本,但要等)。現在有數字了:發布本身 91%,而 `0 */2` 的時事路徑

   所以這是主頻道專案自己的事。
2. **給 `news_dept` 掛 `YT_QUOTA_RESERVE=23650`**(最小、可逆)。
   效果不是讓它發得成,是讓它**明確地不發**,而不是跑到 `videos.post` 才被拒 ——
   現在每次失敗都已經付出了產稿與渲染的成本。
   ⚠️ 這是排程變更,照 CLAUDE.md 屬「新增類型的正式機變更」→ **要先問 Carson**,本檔不自行執行。
3. **降低每支的配額成本**。`captions.post` 400/支 = 4,400/日 = 17% 的天花板。
   如果字幕可以改成上傳時內嵌而不是另外呼叫,那是 4,400 units 的空間。**沒查過可行性,只是點出來。**
