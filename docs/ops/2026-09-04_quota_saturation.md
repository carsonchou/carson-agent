# 主頻道配額已飽和:發布本身吃掉 91%(2026-09-04,從帳本實算)

> 一句話:**不是有東西壞了,是擠不進去。** 近六天有兩天花到**剛好等於天花板**,
> 而今天有一條發布路徑被拒兩次。任何「再多發一支」的計畫都要先過這一關。

## 實算(來源:`quota_meter` 帳本的 `by_op`,不是估的)

每支已發布長片的**真實**配額成本:

| 操作 | units | 說明 |
|---|---|---|
| `videos.post` | 1,600 | 上傳本體 |
| `captions.post` | 400 | 字幕 |
| `thumbnails/set.post` | ~100 | 縮圖 |
| **每支合計** | **≈ 2,100** | 三項都嚴格隨發布數等比例變動 |

⚠️ **`playlistItems.post` 不算在每支成本裡,我第一版算錯了。**
三天都發 11 支,而它是 **09-01 <600 / 09-02 600 / 09-03 1,900** —— **不隨發布數變動**,
所以它是另一支工作(播放清單同步)的花費,不是單支發布的一部分。
把它除以 11 攤成「每支 ~50」是**歸錯類**,會讓單支成本看起來比實際穩定。
(產線常數 `PUBLISH_UNIT_COST = 2,150` 對得上 2,100 加一點餘裕,那是它該有的樣子。)

排程發布量 = 11 支/日(`18:00 --max 1` + `18:30 --max 10`)
⇒ **11 × 2,100 = 23,100 = 天花板 26,001 的 88.8%**(用產線常數 2,150 算是 23,650 = 91.0%,兩個都對,差在有沒有留餘裕)
(這正是好幾支排程掛 `YT_QUOTA_RESERVE=23650` 的由來 —— 那個數字不是隨手挑的。)

`news_dept.py` 排在 `0 */2 * * *` + 平日 09:35/11:35/13:35,發片走 `videos.post`(1,600)
**且沒有掛 `YT_QUOTA_RESERVE`**。它一支就吃掉非發布預算的 **68%**。
⇒ **在現行天花板下,「排程發布 11 支」和「時事即時發布」在結構上不能並存。**

## 三件可以做的,成本與可逆性都不同

1. **提額申請**(最根本,但要等)。現在有數字了:發布本身 91%,而 `0 */2` 的時事路徑
   結構上永遠擠不進去。ch2/ch3 在**另一個 Cloud 專案**(881902283633,從沒申請、還是預設 10,000),
   與主頻道 524513894332 **兩份獨立額度互不影響**(memory `yt-quota-is-per-cloud-project`)——
   所以這是主頻道專案自己的事。
2. **給 `news_dept` 掛 `YT_QUOTA_RESERVE=23650`**(最小、可逆)。
   效果不是讓它發得成,是讓它**明確地不發**,而不是跑到 `videos.post` 才被拒 ——
   現在每次失敗都已經付出了產稿與渲染的成本。
   ⚠️ 這是排程變更,照 CLAUDE.md 屬「新增類型的正式機變更」→ **要先問 Carson**,本檔不自行執行。
3. **降低每支的配額成本**。`captions.post` 400/支 = 4,400/日 = 17% 的天花板。
   如果字幕可以改成上傳時內嵌而不是另外呼叫,那是 4,400 units 的空間。**沒查過可行性,只是點出來。**
