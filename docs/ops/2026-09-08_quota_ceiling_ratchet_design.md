## 根因:一個變數扛了兩個概念

`effective_limit()` 同時是:
- **A. 我們相信 Google 允許多少**(應該來自外部:Cloud console / API)
- **B. 我們觀測到自己花到多少**(來自帳本)

現在只有 B 餵它,而 B 被 A 的執行結果(閘門)夾住。**修法的形狀是把兩者拆開**,
不是去改 `_scan()` 的算式。

## 候選方案

### 方案 1(推薦):核定值升格為第一級輸入,帶出處與日期

帳本加一筆非日期的紀錄:

```json
"granted": {"value": 50000, "source": "cloud-console", "asserted_on": "2026-09-08",
            "by": "carson", "note": "IAM & Admin > Quotas 頁面實抄"}
```

閘門改用 `gate_limit()`:

```
gate_limit() = max(effective_limit(), granted.value)   當 granted.asserted_on >= ceil_day
             = effective_limit()                        其餘
```

- `effective_limit()` **完全不動**(它繼續代表「觀測到的」,是安全下界)
- 真牆若出現在更低的水位,`ceil` 會下移並使 `granted` 過期 ⇒ **降額仍跟得下**
- 沒有任何自動探牆,不花一 unit

**必須一起想清楚的三件**(驗證員要回答):
1. **`granted` 說謊時會怎樣**:值設得比真配額高 ⇒ 花進真 403 ⇒ 08-27 那種重試風暴。
   現在的碼有沒有「撞到配額錯誤就停止該批次」的抑制?**沒有的話,方案 1 不可以單獨上。**
2. **陳舊政策**:`asserted_on` 多久算過期?過期後退回 `effective_limit()` 還是繼續用?
   (退回=無聲降回 26,001,又是「資料掉了不是訊號」那個病。)
3. **要不要限制單次抬升幅度**(例如一次只准 +20%),用階梯換取真 403 的曝險上限。

### 方案 2:用 Service Usage API 自動讀核定值

`serviceusage.services.consumerQuotaMetrics.list`,專案 `524513894332`,
指標 `youtube.googleapis.com/quota/default`。**零 YouTube 配額**(不同服務)。

🔴 **現有憑證做不到**(已實查):`token.json` / `token_analytics.json` / `token_manage.json`
三個 scope 清單**全是 YouTube 範圍**,沒有 `cloud-platform`。
⇒ 需要新的 OAuth 同意或服務帳戶 = **要 Carson 動手,且屬於新增憑證**。

未驗:該 API 對這個專案**是否真的吐得出「核定值」**(而不是只有預設值/用量)。
上之前必須先用一次唯讀呼叫確認,否則就是照文件憑空寫。

### 方案 3(最小、可與 1 併行):把「升不上去」變成會出聲的事

不改任何閘門行為,只加一個**正向輸出**的檢查:
當 `ceil_day` 距今超過 N 天、且期間有 ≥1 天 spent 剛好等於 `effective_limit()`
⇒ 每日在 ops_log 印一行「天花板已凍結 N 天,期間 M 天貼頂,期間自我拒絕 K 次」。

- 它**不解決**問題,但讓「提額核准了卻沒反應」這件事**不再靜默**
- 判準符合 `dispatch.md`「規則要嘛是檢查、要嘛是期望」:它會產生輸出,不是有事才響
- ⚠️ 它**不可以**用「有沒有撞牆」當條件(那是第十一種)。用的是
  **自我拒絕次數 + 貼頂天數**,那兩個我們自己記得到
