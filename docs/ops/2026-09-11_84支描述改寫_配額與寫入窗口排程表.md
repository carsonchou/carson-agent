### (a) 本地帳本的水位 —— 我量得到

檔案 `youtube_channel/STUDIO/quota_meter.json`,離線讀,零 API。
本回合我量了兩次,**中間它自己動了**:

| 量測時刻(台北) | `effective_limit()` | `spent()` | `remaining()` |
|---|---|---|---|
| 11:4x | 26,027 | 26,027 | **0** |
| 12:0x | **26,280** | 26,280 | **0** |

20 分鐘內 +253,而天花板**同步跟上**,`remaining()` 兩次都是 0。

機制(`scripts/quota_meter.py:561 effective_limit()`):

```
floor, ceil, floor_since, *_ = _scan()
if ceil: return max(ceil, floor_since or 0)
```

`ceil` 與 `floor_since` **兩個來源都取自 `spent`**。
⇒ 天花板 = 歷史最高水位 ⇒ **花最多的那一天,`remaining()` 在定義上必然是 0**,
與 Google 實際給多少完全無關。這是閉環,不是量測。

`docs/ops/quota-ceiling-watch.state.json` 仍寫 `{"effective": 26001, ..., "checked_at": "2026-09-10 15:20"}`
—— **已落後現況 279 units**,引用它會拿到過期值。

### 怎麼確認「停在第幾支」而不是「以為做完了」

**唯一權威 = 時間戳檔**,不是 stdout,也不是 DONE 檔:

```
docs/ops/2026-09-11_84支更正句改寫_寫入時間戳.jsonl
```

(`fix_period_disclaimer.py:344 STAMP`,`:358 _stamp()` **以 append 模式逐行寫**,
每支落 `sent` 與 `ok` 兩行;`sent` 在 `execute()` **之前**就落盤 ——
「送出了但回應丟了」這種最危險的情況因此有紀錄。這個設計是對的,不要動它。)

判讀規則(照抄):

| 該支的紀錄 | 判定 | 下一步 |
|---|---|---|
| 有 `sent`,有 `ok` | **確定已寫入** | 列入 T1/T2 回讀母體 |
| 有 `sent`,有 `error` | 🔴 **狀態未知** | **逐支回讀判定**,不准假設失敗、也不准假設成功 |
| 有 `sent`,兩者都沒有 | 🔴 程序被殺在 `execute()` 中間 | 同上,逐支回讀 |
| 連 `sent` 都沒有 | **確定沒送出** | 直接排進下一輪 |

「停在第幾支」= `sent` 行數(不是 `ok` 行數)。
「做完了幾支」= `ok` 行數。**這兩個數字不相等才是正常的**,相等只是剛好沒出事。

🔴 **不准用「印出來的那句總結」當進度依據** —— memory `only-what-lands-on-disk-exists`:
判準是「這件事現在有沒有一個檔案指得出來」。
🔴 **也不准用 `STUDIO/period_disclaimer_done.json` 當進度依據** ——
那是插入模式的狀態檔,`DONE.write_text(...)` 在迴圈**之外**且非原子
(memory `write-truncates-before-it-fails`:寫到一半掛掉會剩 0 bytes,
而**空檔對下游是合法的「零筆」,零訊號**)。改寫模式的母體**就是**這個檔,
它壞掉的後果是「母體變空」而不是「進度歸零」—— 更難發現。
**每輪開跑前先記下它的 md5 與長度,收工再核一次。**
