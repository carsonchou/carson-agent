## 0. 緣起與範圍
Carson 09-15 指示:「開始設計字幕/章節回填併入 84 支治理機制的方案」。背景是 09-15 品質稽核(`yt_quality_audit_report.md`)點名的字幕早 3 秒偏移、章節 64 秒偏移兩項缺陷,對應的回填工具是:
- `fix_caption_drift.py`(字幕回填)
- `desc_chapters_backfill.py`(章節回填,`youtube_channel/scripts/` 與 `yt_ch2/scripts/` 兩份已分歧的複本)

本文件只做**設計**,不執行任何寫入,也不凍結任何母體。凍結、STAMP 格式定案、canary 批次大小等**執行細節**留給 wF:p3(既有機制把關人)在裁決後另行落檔到它自己的把關清單(`docs/ops/2026-09-12_84支寫入把關清單_wF-p3.md`,1479 行,本 session 未逐行讀,只讀過 `research-84-governance` agent 的摘要,細節以 wF:p3 手上的正本為準)。

## 2. 設計原則(沿用本頻道已踩過的坑,逐條標來源)
1. **母體會自己長大,不准用「加例外」解**——84 campaign 自己的解法是凍結 DONE 快照到 sha1,兩支回填工具的候選清單同樣是持續成長的帳本(每日 15:05 cron 母體滾動),必須比照凍結,不比照加白名單。
2. **CAS 寫入(tmp→readback→os.replace)是全庫規則,不分正式機/memory/scratchpad**——兩支回填工具目前違反,這是**進場前必須先補的地板**,不是可以留到之後的 nice-to-have(memory `write-truncates-before-it-fails`、`rule-scope-not-narrowed-by-the-bound`)。
3. **安全網不能先於它保護的動作被驗證**——84 campaign 自己的還原工具目前也只驗過合成 fixture(因為真實 `*.pre_rewrite.json`/STAMP 都是 0 筆),把兩支從沒寫過一筆的回填工具疊上去,等於在一個**自己也沒被真實驗證過**的機制上再加兩層未驗證的東西。這是本提案建議「先跑通 84 campaign 至少一次真實 canary,再談回填併入」的直接依據(見 §4)。
4. **檔名慣例衝突要在動手前消掉,不要留到出事才發現**——`.pre_rewrite.json` vs `<vid>.json` 已被研究 agent 點名同目錄可能互相覆蓋/誤讀,兩邊都要改成同一命名規則。
5. **識別碼/凍結基準不准用猜的**——140 vs 185(章節)、89 vs 28(字幕)這兩組數字對應到不同基準檔,本文件不替 wF:p3 選一個,列成待裁決項(§3)。

## 3. 待裁決項(本 session 不單方面決定,列出來源與利害)

**D1、章節回填凍結要對齊哪個基準?**
- 對 `desc_chapters_fixed.json`(140)還是 `desc_chapters_done.json`(185)?兩個檔案語意不同(`fixed`=已判定要修的清單,`done`=已處理完的清單),但研究 agent 沒能百分之百確認兩者的欄位定義是否与 84 campaign 的 DONE 語意等價。**建議**:這件事只有 wF:p3(既有機制的作者)能準確回答,不應由本 session 猜。

**D2、`yt_ch2/scripts/desc_chapters_backfill.py` 怎麼處理?**
- 選項 A:先補齊 `yt_ch2` 缺的配額中止 `break`,兩份一起納管。
- 選項 B:比照本 session 09-15 已做的 `force_key` 擴大決定(commit `4f643217`),明確排除 `yt_ch2`,只納管主頻道那份,`yt_ch2` 另案處理。
- **建議 B**(理由:`yt_ch2` 是另一條產線,已有自己的分歧史,混進來會讓本次範圍失焦;且選項 A 需要額外驗證 `yt_ch2` 的配額帳本語意是否與主頻道一致,那是另一個獨立稽核任務)。

**D3、併入「同一個」pipeline 實例,還是「共用元件、各自母體」的平行 pipeline?**
- 選項 A(同一實例):字幕/章節/描述更正句三種候選共用同一份候選清單、同一組 STAMP 命名空間。
- 選項 B(共用元件、分母體):三者各自的候選清單、STAMP 命名空間、canary 批次分開跑,但共用同一套底層元件——CAS 寫入 helper、還原工具(需要先驗證能否泛化到字幕/章節格式,還原工具目前是綁描述欄格式寫的)、配額帳本的 key 命名慣例(`videos.put`)。
- **建議 B**。理由:三種內容型態的寫入 payload 完全不同(描述文字 vs 字幕時間軸 vs 章節時間戳),混進同一候選清單會讓「這支影片為什麼被擋/被回滾」的歸因變模糊(對照 memory `load-bearing-line-needs-mutation`——出事時要能指出是哪一類型、哪一行造成的);分母體、共用經過驗證的元件,可以省掉重造轮子的成本,又不犧牲可歸因性。
- 還原工具能否直接泛化到字幕/章節格式**本身需要一輪獨立驗證**,不能假設它「反正邏輯差不多」就直接套用(memory `plausible-cause-becomes-fact` 的教訓)。

**D4、時序——現在就開工,還是等 84 campaign 先跑完至少一次真實 canary?**
- **建議**:等。84 campaign 至今零寫入,它的 canary/STAMP/還原工具鏈只驗過合成情境。在自己都沒被實戰驗證的機制上,再疊兩支「連候選清單基準都還沒對齊」的新工具,風險是三線一起卡在同一個未驗證的地基上。**建議排序**:84 campaign 先完成一次真實 canary 批次的端到端寫入+回讀+(如需要)還原,拿到一次正向證據後,再把回填工具接進去(用 §3-D3 的「共用元件」設計,屆時元件已經被 84 campaign 的實戰用過)。
- 這是排序/優先順序判斷,影響到 Carson 對「什麼時候看得到字幕/章節被修好」的預期,**本 session 不單方面拍板,列為要 總督導 確認的項目**。

## 4. 建議的動工順序(若 D4 裁決為「不等」,則跳過第 0 步直接從第 1 步開始)
0. 84 campaign 完成至少一次真實 canary 端到端寫入(現有工作,不在本提案範圍內,只是排序上的前置)。
1. 補地板:兩支回填工具的進度檔改成 tmp→readback→os.replace;`fix_caption_drift.py` 補上寫前備份(命名比照 D5 待定的統一慣例)。這一步不涉及母體/STAMP設計,可以獨立先做,不用等 D1-D4 裁決。
2. 依 D3 裁決結果,設計字幕/章節各自的 STAMP 命名空間 + 候選清單凍結格式(比照 84 campaign 的 sha1 釘住手法)。
3. 依 D1 裁決結果凍結章節回填母體;字幕回填母體同步凍結(89,對 `caption_drift_fixed.json`)。
4. 還原工具泛化到字幕/章節格式,獨立驗證(fresh-context agent,對照 `docs/ops/dispatch.md` §6)。
5. 各自跑一次 canary(比照 84 campaign 的 4 條件 canary),wF:p3 覆核,總督導裁決是否放行 T1。

## 5. 本提案的定位
這是**設計提案**,不是裁決。第 1 步(補 CAS 地板)技術上獨立、風險低、不涉及母體或寫入,建議可以先授權開工;第 2 步以後涉及 D1-D4 四項待裁決,需要 總督導(代表 Carson)與 wF:p3(既有機制作者/把關人)確認後才進入實作派工。
