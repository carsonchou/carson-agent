## 〇、先講三個橫跨看才出現的結構性發現

**逐道盤點看不到這三件 —— 每個 agent 看自己那道時,都會覺得「它有印警告,很好」。**

### 1. 🔴 排程上的每一支腳本,stdout 都進 DEVNULL

`scripts/local_cron.py:282` `stdout=subprocess.DEVNULL`。
而且 `:219` 的抽取正則 `(scripts/[A-Za-z0-9_]+\.py)(.*?)(?:\s*>>|\s*2>|\s*$)`
**明確把指令切在 `>>` 之前** ⇒ crontab 裡每一行寫的 `>> /root/yt/logs/cron.log 2>&1`
**被剝掉且忽略**,而 `logs/cron.log` **根本不存在**(實查)。

⇒ **任何以「印一行紅字」為告警手段的閘門,在排程上是結構性靜默的。**
本次盤到直接中彈的:`brain_score_watch`、`brain_submit_watch`、`brain_miner_watchdog`、
`auditability_coverage` —— 它們「沒事」和「有事」印的東西**都**進黑洞。

⚠️ 這一條不是「某道閘門的 bug」,是**所有閘門共用的那條線斷了**,
而 crontab 的每一行都寫著一個看起來會保存輸出的重導向。**那行字本身在誤導讀者。**

### 2. 只有 2/9 會寫 ops_log,而其中一支(我的)寫入是壞的

`STUDIO/ops_log.txt` 是各部門共用、會留在磁碟上的頻道(12,459 行)。實查九支:

| 落 ops_log | 有推播(ntfy) | 只剩 exit code |
|---|---|---|
| `per_stock_fact_gate`、`auditability_coverage`(壞的) | `fact_guard`、`daily_health`、`brain_submit_watch`、`seeding_watch`、`narration_compliance_watch` | `fact_source_guard`、`brain_score_watch`、`brain_miner_watchdog` |

🔴 **`auditability_coverage.py:294` 寫的是 `sc.log_ops(...)`,而 `studio_common` 沒有這個函式**
(全 repo 20+ 支部門腳本都是 `from ops import log_ops`)。
`AttributeError` 被**同一行的 `except Exception: pass`** 吞掉,而註解寫著
「落 ops_log 失敗不影響判準」—— 那句話對(exit code 判準確實沒受影響),
但代價是 `grep -c 稽核涵蓋 ops_log.txt` = **0**,上線兩天一行都沒寫進去。
**這是我自己兩天前建的那道,而它的檔頭正好在講「每次都要有正向輸出」。**

### 3. exit code 是唯一普遍可用的通道,而它和 crash 混在同一堆

`local_cron.py:250-253` 確實會記 `✗ 失敗 <script>(exit N)` —— 所以 exit code 有留痕。
但近 7 天 `local_cron.log` 有 **37 行 `✗ 失敗`**,
而**「閘門正確地叫了」和「腳本壞掉了」在那一行上長得一模一樣**。
且多數閘門根本不用這個通道:`daily_health.py:541` **無論 warn 與否一律 `return 0`**。

⇒ 三條通道:**stdout 斷了、ops_log 幾乎沒人接、exit code 有雜訊且多數不用。**
**這是「閘門瞎掉」之外的第二種病:閘門沒瞎,但它的叫聲沒有能到達讀者的路。**

## 一、判準的四種形式,以及它們為什麼會漂

| 形式 | 漂移機制 | 半衰期 | 本盤點的實例 |
|---|---|---|---|
| **樣式清單**(關鍵字/正則/黑名單) | 🔴 **被監控物會演化,清單不會** ⇒ 覆蓋率自動衰減,**且衰減時行為完全不變** | 最短 | 舊 prompt 閘門(已換)、`fact_guard`、`narration_compliance_watch` |
| **數值門檻** | ⚠️ 門檻是**用當時的資料校準**的;分佈變了門檻就等同瞎掉 | 中 | `K_ZERO=5`(08-30 校準)、`UPSTREAM_FLOOR=0.50`、`TARGET=2` |
| **結構檢查**(欄位/型別/不變量) | ✅ 綁的是**關係**不是外觀,LLM 換句話說不影響 | 長 | `per_stock_fact_gate`、`scan_ambiguous_zero`(AST)、`auditability_coverage`(HWM) |
| **外部比對**(和另一份資料對帳) | ✅✅ **判準從被監控物本身長出來** ⇒ 對方變,判準自動跟著變 | 最長 | 現行 prompt 閘門(比對 prompt 常數)、`daily_health` 配額段(`_ref` 自適應) |

### 🔴 比「判準是什麼形式」更根本的診斷問句

**「被監控的東西是誰寫的?」**

- **我們自己的確定性程式碼寫的**(欄位名、schema、固定格式)→ **清單型可以**,
  它不會自己變;真要變是我們改的,改的時候會知道。
- **LLM 寫的 / 外部 API 回的 / 人寫的** → **清單型必漂**,
  因為那個作者會持續演化而清單不會,而且**漂的時候不會產生任何訊號**。

九道裡監控 LLM 輸出的有三道:prompt 洩漏(已改成外部比對 ✅)、
捏造數字(已是結構檢查 ✅)、**旁白合規哨(仍是樣式清單 🔴)**。

#### 🔴 那個縫在哪:兩道閘門的分工,以及分工外的那一格

實測(隨機百分比 400 個,餵各自的判準):

#### 這一格不可能靠調容差修好(結構證明,不是判斷)

全域池在 0~200 區間有 **32,947** 個數字,**相鄰間距中位 0.0000 / P90 0.0100**
⇒ 要擋住一個隨機百分比,容差必須小於半個間距(≈0);

**兩個需求差 12,768 倍,沒有任何容差同時滿足。**

⇒ **唯一的修法是縮小池子**,也就是把 `per_stock_fact_gate` 的設計
(「這個數字對得上**這一支片自己**的哪一條 fact」)延伸到非個股體檢內容。
那是**設計改動不是參數調整**,規模與 §六 的第 4 項同級,**不在本輪**。

⚠️ 動它之前的硬性前提(07-17 的教訓,寫在 `fact_source_guard._sourced_unit` docstring 裡):

**9 支原本被擋的編造片變成放行**(含「AI策略回測勝率90」「當沖勝率80」這些真實事故片)。
⇒ **任何對這道閘門的修改,都要先證明已知被擋的案例仍然被擋。**
現成回歸語料:09-08 那次實跑被擋下的 **20 支候選**(清單可用
`daily_publish._factguard_gate(find_candidates(led))` 重跑取得)。

## 七、方法論

1. **回歸語料把「靜默衰減」換成「大聲失敗」,但它有天花板。**
   它證明的是「**還抓得到昨天的案例**」,永遠證不了「抓得到明天的」。
   #4 之所以是範本,關鍵不在語料,在**判準改成從被監控物身上長出來**(比對 prompt 常數)——
   語料只是第二層。**只補語料不換判準來源,買到的是「不會退步」,不是「跟得上」。**
2. **一道閘門有兩種瞎法,而它們的修法相反。**
   ①**判準瞎**(清單追不上)→ 換判準來源;
   ②**叫聲到不了**(stdout 進 DEVNULL / ops_log 沒接 / exit code 混在 crash 裡)→ 修通道。
   ⇒ 盤點必須兩欄分開問。本次九道裡,②比①普遍得多,而②從單道視角看不見。
3. **「校準案例寫在 docstring 裡」不等於有回歸語料。**
   `scan_ambiguous_zero` 的三個校準案例現在一個都命中不到 —— 敘述不會叫,斷言才會。
   同族:`tests/paren_stage/known_gap.py` 選擇留一支**會失敗的測試**而不是一則註解,
   理由寫得很好:「註解會被讀過就忘,失敗的測試每次跑都會叫」。
   ⚠️ **但那個機制有前提:要有東西在跑 `tests/`。** 實查:crontab 沒有、CI 只有一支
   `server-monitor.yml`、git hooks 只有 sample。⇒ **目前沒有東西在跑它。**
   一支沒人執行的失敗測試,和一則註解的差別只剩「下一個人會不會手動跑」。
4. **一個會讓自己的工作看起來更有價值的假設,要當成需要更多證據的假設,不是更少。**
   我幾乎就要寫下「休眠的證據來自那個有盲點的偵測器」——那會是個漂亮的發現。
   測完是假的(31 支全在 7、8 月,9 月 0)。**寫下來之前先去測,是這條唯一的執行方式。**
5. **盤點自己的產出時,找一個沒讀過它的人。** 我知道我那道的 `log_ops` 可能有問題是因為
   我從 ops_log 反查(0 筆命中);而獨立盤點員從程式碼正查也到同一個結論。

# 🔴 更正:§3.3「已證明瞎掉的(1 道)」是錯的 —— 而錯的是我的量測(2026-09-08 09:0x)

總督導裁示「拔掉 `fact_source_guard`」,理由用的是本文件 §3.3。
執行到最後一步、拔掉之後跑驗證時翻車:

## 我錯在哪

`fact_source_guard` 的產線判準是 **`_sourced_unit()`,而它的定義是「舊判定 **AND** 單位判定」**
—— 單位化**只能拿掉憑據,永遠不能新增**(該函式 docstring 明寫這是結構性單調保證,
因為第一版寫成「直接改用同單位子池」時,**9 支原本被擋的編造片變成放行**)。

**我的探針只量了前半段**(`_sourced()`,無單位池),得到 100% 就寫下「全面飽和、為任何數字背書」。
產線走的是兩段的 AND。

## 修正後的數字(用產線真正呼叫的那個函式重量)

| 數字類別 | `_sourced_unit`(產線) | 我先前用的 `_sourced` |
|---|---|---|
| 百分比 0~200 | **100% 放行** | 100% |
| 大百分比 200~10000 | **100% 放行** | 100% |
| **金額 1~10000 萬** | **2.0% 放行 ⇒ 擋掉 98%** | 100%(**錯**) |

⇒ **「已證明瞎」對百分比成立,對金額完全不成立。**
而金額正是 2026-07-17 加 `_sourced_unit` 要治的那一類
(docstring 實案:「多賺 37 萬」撞池裡的 36.8/37.1 百分比),也正是被擋那 20 支的內容。

## 所以正確的結論是

**不能拔。** 拔掉會移除**金額型宣稱**上 98% 有效的防護,而那一類覆蓋**全部內容含 749 支 Shorts**
—— 正是 `per_stock_fact_gate` 明文不管的那一群(`check():638`「非個股體檢片,本閘門不適用」)。

正確的描述是:**這道閘門在百分比上瞎、在金額上有效**,不是「整道瞎」。
它自己的 docstring 早就誠實列出能力邊界(治得了什麼、治不了什麼),
是**我沒讀完就用一個更省事的探針去驗證它**。

## 這次踩的是哪一個坑

**量了不等於量對 —— 而這次是「量了那個函式的上游那一半」。**
`_sourced` 和 `_sourced_unit` 名字相近、都在同一個檔、都回 bool,
而它們之間差著整個判準的一半。我測到 100% 時**沒有回頭問「產線呼叫的是這一個嗎」**。

⚠️ 而繼承來的那句「隨機 400 個百分比通過率 100%」(`per_stock_fact_gate.py:20`)
**大概率也是這樣量出來的** —— 它對百分比碰巧是對的,所以沒人發現方法有問題。
**一個碰巧正確的結論會替一個錯誤的方法背書**,而那個方法後來被我用在金額上就出錯了。

⇒ 判準:**驗證一道閘門之前,先用 AST 或實跑確認「產線到底呼叫哪一個函式」**,
不要挑一個名字看起來對的。更省事的探針要付的代價,是它可能量的是別的東西。

⚠️ 附帶要記的:我差一點就以「已證明瞎」為由拔掉一道**每天在擋 22% 候選**的閘門,
而擋下來的內容看起來正是產線在編造金額。**救回它的不是警覺,是「拔完跑一次驗證」這個動作。**
