# 時事發布連續死三天 —— 不是額度不夠,是配額日內的**排序**(2026-09-04,督導 wF:p1)

## 一句話

**時事發布最後一次成功是 09-01 09:38,之後連續 10 次全部因配額失敗。**
而它不是被「額度不夠」擋住的,是被**排在發布後面**擋住的 —— 同樣的總額度、
不同的順序,結果完全不同。這件事不會自己好,而且**唯一的訊號是沒人看的 ops_log ⚠️ 行**。

## 🔴 先讀:「配額失敗」不是 Google 拒絕我們(2026-09-04 23:30 補,督導 wF:p1)

本檔下面所有「配額失敗」都是 **我方客戶端閘門**擋的,**不是 Google 的 403**。
`STUDIO/quota_meter.json` 的 `rejected_calls`:

| 日期 | spent | rejected_calls(Google 真拒絕) |
|---|---|---|
| 08-31 | 26,001 | **31** ← 唯一一天有真 403 |
| 09-01 | 25,206 | 0 |
| 09-02 | 24,673 | 0 |
| 09-03 | **26,001** | **0** ← 花到剛好等於天花板,而 Google 一次都沒拒絕 |
| 09-04 | 24,932 | 0 |

⇒ 我們是**拿自己推出來的天花板(26,001)在擋自己**。而那個數字是三個互不一致的錨點之一
(25,999 / 26,001 / 24,374),全部從自家觀測反推,**從來沒有人去 Cloud console 抄過官方核定值**。

**08-31 的 31 次真 403 證明天花板確實存在且大約在那裡** —— 這個推估不是憑空的。
但 09-03 花到「剛好 26,001 而零拒絕」是**自家閘門畫的線**,不是撞到牆。
兩天長得一樣,證據種類完全不同。

⇒ 因此本檔的結論要這樣講才精確:
**時事發布不是被 Google 擋住的,是被「我們對配額日內優先序的安排」加上
「我們自己估的天花板」一起擋住的。** 前者可以重排,後者可以去 console 查證。
⚠️ 對外文件尤其不可以寫成 `were refused`(無主詞)—— 那會讓讀者以為是 Google 拒絕,
而近四天 Google 一次都沒拒絕過。

| 日期 | 結果 |
|---|---|
| 08-28 ~ 09-01 | 成功 8 次(最後一次 **09-01 09:38** `youtu.be/2uxiCncFQ_M`) |
| 09-01 10:02 / 11:38 | ❌ 今日剩 **0** / **0** |

`videos.post` 需要 **1,600**。十次全部差在 172~1,600 之間 —— **沒有一次接近過**。

## 三、根因:配額日在台北 15:00 換,而發布排在配額日的開頭

```
太平洋配額日 D  =  台北 15:00 (D)  →  台北 15:00 (D+1)
                   ↑
                   18:00 / 18:30 發布 11 支 ≈ 23,100 units(天花板 26,001 的 88.8%)
                   ↓ 之後的 21 小時只剩 ~1,000~2,900
                   00:01 04:03 06:02 08:01 09:38 10:02 11:38 13:37 14:01 ← 時事的所有時段
```

時事發布的**每一個**時段(觀測到的 00:01~14:01 台北)都落在同一個配額日、
而且都在那兩批發布**之後**。它拿到的永遠是剩下的。

## 四、🔴 這不是疏漏,是一個已經寫下來的優先序 —— 只是它變成綁定條件了

`deploy/crontab.txt:360-366` 白紙黑字:

> `2026-08-30 09:15 → 17:30`:09:15 位在配額日尾端…**實測 daily_publish 因配額失敗 7/33 次、
> 其中 09 點就佔 5 次 = 5 支片沒發出去。**18:00 = …配額日才過 3 小時、額度最足…
> 而且排在 18:30 批次之前 —— **個股體檢是頻道引擎,額度不足時該讓它先發。**

⇒ 把發布移到台北 18:00 是**有實據的正確決定**,而且它解決的正是同一個病(當時是發布在挨餓)。
問題不在那個決定,在於**它是在日花費 18k~22k 的年代做的**。08-31 起日花費頂到 25k~26k,
「先發的人拿滿、後面的人拿剩」這個規則沒變,但「剩下的」從 4k~8k 變成 0~1.4k,
**跨過了 1,600 這條線**。

**同一條規則,在不同的花費水位下,一邊是無害的優先序、一邊是整個部門歸零。**
而中間沒有任何一天出現「規則改變了」的訊號。

## 五、所以這是提額申請的一項具體損害,不只是「我們撞到天花板」

申請書目前的論證是飽和度(發布吃掉天花板 88.8~91%)。這裡多一個可指名的後果:
**一個部門連續三天以上零產出,且不會自我恢復。**
飽和度是比率,這個是事件;審核的人對事件比對比率有感。

## 六、不要現在動排程

移發布時段會**重建一個已經解掉的問題**(上面那 7/33)。而且 09:15 那個實據是量過的,
我手上沒有同等級的證據說「時事片值得排在體檢片前面」。

⚠️ 尤其:**時事發布已經死了三天,所以我們沒有它近期的價值資料。**
「它值不值 1,600 units」現在無法回答 —— 不是答案是零,是**沒有觀測**。
不要拿「死了三天也沒人反映」當作它不重要的證據,那正是
[[distribution-before-quality]] 那個形狀:沒有回饋管道的東西可以無限期地不出事。

真要換,最便宜的一刀是 `daily_publish --max 10` → `9`,釋出 ≈2,450 units(1×videos.post
+ captions),代價是每天少一支長片 ≈ 4~7 觀看小時(memory `yt-marginal-value-per-video`)。
**這是 Carson 的取捨,不是我的:它拿一支已知價值的片,換一支未知價值的片。**

## 七、附:crontab 裡一句沒劃邊界的錯前提

`deploy/crontab.txt:174`:

> 這支只補長片…**produce_batch 不吃 YouTube 配額(只走 LLM/OpenRouter),故可安全加班。**

**條件為真、無條件為假。** `produce_batch.py:6265-6266` 的時事路徑:

```python
yt = dp.get_service()
vid = dp.upload_one(yt, slug, priv)      # videos.insert = 1,600 units
```

ops_log 裡每一則 `時事發布｜⚠️ 即時發布失敗:quota exhausted` 都是從這裡出來的。
一般產稿路徑確實不吃配額,所以那句話大部分時候是對的 —— 而「故可安全加班」
這個結論是建立在無條件版本上的。同一個形狀今天已經記過一次
(memory `verification-claims-in-commit-messages`:**未劃邊界的真話會被合理地過度延伸**)。

⇒ 建議把那句改成「產稿路徑不吃配額;時事即時發布路徑吃 1,600」,
不改行為,只讓下一個看排程的人不會據此加班到撞配額。
