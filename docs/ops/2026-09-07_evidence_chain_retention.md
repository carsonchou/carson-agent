### 2.1 先更正一個我自己的中間結論

我派出去的 subagent 回報「`stock_checkup_facts.json` 只留**彙整後的數字**,不是原始回應」,

那個檔的 `results` 區(**7,742 筆**)每一筆長這樣:

```

claim       近20年含息還原總報酬 8728.8%（年化 25.1%、最大回撤 -46.5%、卡瑪比率 0.54）
```

### 2.4 而它的失敗形態正好是「一次全滅、零訊號」

   ⇒ 這是交接檔第 1 條(「沒有 R」vs「我沒查到 R」)的升級版:
   **連「查過哪裡」都完整誠實,結論仍可以是錯的,如果那份清單漏了一整類持有者。**

2. **有 R 但取不到,和沒有 R,在「有沒有」這個問句下長得一樣。**
   `contentDetails.caption=true` 說得出「有字幕軌」,說不出「拿得回來」。
   零配額的網頁探針證了存在、抓內容回 0 bytes;要到 `captions.download` 才知道真的取得回來。
   ⇒ **問「在不在」不夠,要問「現在把它拿出來給我看」。**

3. **兩個儀器、兩個陰性對照,才敢說那 250 支是真的有。**
   `videos.list` 的陰性對照是 Shorts(99/100 false,因為產線明文跳過);
   `captions.list` 的陰性對照是一支 `caption=false` 的長片(0 軌)。
   沒有陰性對照時,「250/305」和「儀器對什麼都說有」分不開。

4. **量了不等於量對(第二次)。** 代號抽取 `r"(\d{4,6})"` 把
   「台積電**2330**」+「**20**年翻84倍」讀成 `233020`,做出「38.3% 事實已不在」這個假結論

   ⇒ **一個數字如果剛好證實你正在論證的東西,那是要多看一眼的理由,不是少看一眼的理由。**

6. **一個備份腳本漏掉一個檔,和它從來沒被寫過,在 log 上長得一樣。**
   `snapshot_studio.py` 每天 04:05 準時跑、印「7/7 個檔」、rc=0、七天輪替正常運轉 —— 64 天。
   它從頭到尾沒有任何一個表面會顯示「你漏了那個 17MB 的檔」。

## 十、補記:Shorts `.srt` 的「672 組違反配對」是假警報(2026-09-08 00:2x)

survival 量測回報:遷移後 Shorts `.srt` **272/377**,而且**不單調(違反配對 672 組)**,
判讀寫成「這不是清理形狀,是隨機/零星缺漏」。

**查下去是反的:那 105 個不是掉了,是從來沒被產生過。**

`.srt` 全 repo 只有 `make_video.write_srt_for_slug()` 一個地方會寫(`make_video.py:514`),
而產線唯一的呼叫點是 `daily_publish.py:1015`:

```python
_srt = _mv.write_srt_for_slug(slug) if (not is_short and _ab_upload) else None
```

**`not is_short`** —— Shorts 在現行產線根本不產 `.srt`
(另兩個呼叫點 `fix_caption_drift.py:56` / `fix_captions_sync.py:106` 是手動的一次性修補腳本)。

按發布半月拉開,切點乾淨到沒有懸念:

| 發布半月 | 有 `.srt` | 無 `.srt` |
|---|---|---|
| 2026-07 上 | **185** | 0 |
| 2026-07 下 | 54 | 17 |
| 2026-08 上 | **0** | 34 |
| 2026-08 下 | **0** | 41 |
| 2026-09 上 | **0** | 1 |

⇒ 07 月底那道 `not is_short` 上線之後,**Shorts 一支 `.srt` 都沒再產過**。
對得上 `daily_publish.py:993` 那段 2026-07-28 的配額註解
(「只給長片上字幕…省下 2 支×400 = 800 units/日」)。

### 🔴 這條要記的方法論:單調性檢定量的是「缺失」,而**「缺失」把「沒了」和「沒產生過」混在一起**

那個檢定是 09-06 建立的,設計目的是分辨「滾動清理」與「一次性事件」,
它做得很好 —— **但它預設每一支片都應該有那個檔**。
產生端一改,「應該有」的母體就變了,而檢定不知道,於是把一次**產生端的變更**
報成「隨機零星缺漏」,還附上 672 這個很有份量的數字。

- 這和 memory `verification-that-cannot-fail`「**分母跟著處置一起動**」是同一族:
  那裡是分母隨處置縮水,這裡是**分母隨產線版本變動**,兩者都讓指標講出與事實相反的話。
- 判準:**跑任何「存活率 / 覆蓋率」之前,先確認分母是「本來就該存在的那一群」**,
  而那一群由**產生端**定義,不是由「其他兄弟檔案都有」推定。
  問句是:**「這個檔,對這一支片,當初到底有沒有被產生?」**
- ⚠️ 危險的地方在於它**看起來像壞消息**,而壞消息比好消息更容易被直接採信。
  672 這個數字如果沒去查,會變成「有東西在零星刪 srt」的搜捕令 ——
  同 memory `yt-readback-stale-cache` 那次「假設外部有攻擊者,比假設自己的儀器不準更容易想到」。

⇒ 本報告 §四「沒有任何時間門檻碰得到證據原檔」的結論**不受影響,反而更乾淨**:
唯一一個看起來像反例的訊號,查完是產生端變更。
