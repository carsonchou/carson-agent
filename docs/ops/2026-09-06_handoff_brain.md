## 方法論(唯一會隨 context 消失的東西)

**修一個 fail-open,本身就是高缺陷密度的工作。** 十一輪驗證,前十輪都找到東西,
**其中七個是我在修的過程中新造的**,而每一輪交出去時我都認為已經好了、測試都是綠的。

「檢查不會叫」這兩天出現在**五層**:產線程式碼 → 我的修法 → 我用來證明修法有效的
測試 → 監看產線的哨 → 哨的測試。第三層最難抓(斷言看起來正確,壞的是它**有沒有機會
被求值**);判準:**在壞版本上跑一次,看那句斷言 FAIL 的原因是不是你寫的那個。**

**盯哨那件示範了一個更深的形狀:我在同一支檔案裡把同一個錯犯了三次**,每次都以為
換到了權威訊號 —— 鎖在不在 → 帳本有沒有長(429 時 miner 活著也不長,佔歷史 66.3%)
→ `src=alpha_cron`(只有搶到鎖才寫,219 筆裡只有 5 筆)。
⇒ **用一個產生條件比事件更窄的訊號去代表那個事件**,是這一族最頑固的變形。
⇒ 所以 D 項的規格是「**先造訊號,再造哨**」:在 `brain_alpha_cron.py` 的
`claim_lock()` **之前**無條件寫一行心跳,**沒有那一步就不要做哨**。
