## 二、暴露面(實測,不是估的)

以 09-08 22:35 快照(9,784 條)與帳本(12,372 列):

```
用 group_backfill 的：平台 3 條、帳本 3 列        ← 判反只在這幾條上發生
完全沒有 backfill( 的：平台 281 條                ← 這些在舊版共用一個 `?` 桶,被去重成一條
```

⇒ **頻率很低、單次後果很大**:`LL7Z3lKv` 就是那 3 條之一,而它差一點被推薦出去。
不可以因為「只有 3 條」就降級 —— 3 條裡已經有 1 條實際咬到了。

## 三、🔴 `runway.py` 身上有**兩個方向相反**的偏差,不會互相抵消

| 偏差 | 方向 | 來源 |
|---|---|---|
| 池子只有帳本 | 跑道**偏短**(少看到候選) | `:381` |
| `numerator` 認不出 `group_backfill` | 跑道**偏長**(該排除的沒排除) | `:87` |

兩者**不是同一組樣本**(前者少 6 條、後者多算 3 條裡的一部分),
所以「一個偏高一個偏低,大概還好」是站不住的 —— **只修一個會讓另一個變得更明顯**,
而兩個都不修時,那個數字的誤差方向連號都定不了。

⇒ 這也是為什麼**不建議只修池子**:要修就兩條規則一起收斂。

## 四、成本(逐項,含實際觸點)

### 步驟 1:把 `numerator()` 搬到 `brain_auto`(共用地基),三處改成引用
- 觸點:新增 1 處、刪除 3 處定義、4 個檔案改 import。`family_key()` 一起搬。
- **為什麼搬到 `brain_auto` 而不是從 `pick_next` import**:`hybrid_miner` / `universe_sweep`
  是挖礦側的,讓它們為了一個正則去 import 挑片器,等於把挑片器的相依(含 `reconcile`、
  平台快照)拖進挖礦程序。地基放地基,不要讓下游互相 import。
- 風險:低。純函式、無狀態。
- **陰性對照**:改完各拿一條 `group_backfill` 的真實式子餵四個呼叫端,
  斷言分組結果**改變了**(沒改變 = 這次改動什麼也沒做到)。

### 步驟 2:`runway.py` 的候選池改成呼叫 `build_pool` + `dedup_by_numerator`
- 觸點比看起來小:`:381-393` 共 13 行,下游只用到 `alpha_id` / `expr` / `fitness`
  三個欄位(`:401` `:407` `:423` `:426`),把 `c["result"].get("fitness")`
  換成 `c.get("fitness")` 即可 —— **不需要動它的相關度計算與輸出格式**。
- 風險:中。它是「還能不能再交」的判斷工具,輸出的數字有人引用。
- **陰性對照(這一步的重點)**:改動前後**用同一份快照與帳本各跑一次**,
  逐條 diff `accepted` / `grey` / `rejected` 三張清單。
  預期:accepted 會多出平台側候選、且**至少一條**因 `numerator` 修正而被移出。
  **如果三張清單一模一樣,代表這次改動沒有生效**(而它會長得像成功)。
- ⚠️ `runway.py` 有 `--allow-incomplete-pool` 這道自帶的守衛,改完要確認它仍然
  擋得住「池子少一條」——不要在合併時把它一起改寬了。
