## 七、順手撿到的第三個缺陷:同一條 alpha 被算成兩條(別名)

驗證員在核 `runway` 時撿到的,**評估初稿完全沒提**:

```
runway 候選 674 條 → 唯一 alpha_id 520   ⇒ 重複 154 條(23%)
--top 60 之內      → 唯一 alpha_id  52   ⇒ 重複   8 條(13%)
```

成因是**平台對同一個欄位收兩個別名**,帳本兩個都記了、平台回**同一個 alpha_id**:

```
j23Rk60o  fit=1.85  ts_backfill(anl4_fs_detail_estimates_basic_af_v4_nd_eps_mean/cap, 120)
j23Rk60o  fit=1.85  ts_backfill(anl4_afv4_eps_mean/cap, 120)
```

`numerator()` 拿**欄位名**當鍵,所以同一個因子的兩個別名 = 兩個鍵 = 兩條候選。
🔴 **新版 `numerator()` 修不掉這個** —— `\w*backfill` + hash 解的是「認不認得出來」,
別名問題和正則無關。要修得靠 alpha_id 去重,或建別名對映表。

**方向要講清楚**(不要重犯上面 (a) 那個錯):重複列會在相關度那關撞到自己
(`corr(p, p) = 1.0`)⇒ 落進 `rejected`,所以 **`accepted` 不會被灌水**、
`days = len(accepted)//2` 不會偏長。代價是另外兩件:
① `--top` 的評估名額被重複佔掉約 13%(只看得到 52 條不同的 alpha)⇒ 跑道估計**偏保守**;
② `:458` 報表的「不安全 N 條」含自我重複,那個數字會誤導讀者。

⚠️ **證據等級**:重複計數(674/520、60/52、那幾對式子)是**實算的**;
「重複列落進 rejected」是**讀碼推的,沒有實跑證據**(跑 `runway` 要連平台抓 PnL)。
要證實得實跑一輪或用 stub 餵 `corr`。**在證實之前不要拿它當前提。**
