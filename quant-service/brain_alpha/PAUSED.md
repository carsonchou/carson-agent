- [ ] **① 改簽章前,對整個 repo grep 呼叫端** —— 不是只 grep 你正在改的那個目錄。
      漏掉一個就足以打死一支排程,而 **tuple 恆為 truthy** 會讓 `if not x` 和
      `x is None` 兩種判斷**同時**失效 ⇒ 成功與失敗路徑都炸。
      更安全的做法:**簽章根本不要動**,新行為開新函式,舊名字留成薄包裝。
- [ ] **② 不要在修崩潰的同時放寬合約** —— KeyError → 收成預設值、例外 → `or 1`、
      `else <原值>`,這三個動作看起來最保守,實際最寬鬆。崩潰很吵所以像缺陷,
      但它站在安全那一側。**換掉它時預設值必須落在「不通過」那一側。**
- [ ] **③ 防「一定叫」:問一句「有沒有一整類正常輸入現在會被擋掉?」**
      把 fail-open 修成 fail-closed 很容易滑過頭。特別檢查邊界常數是不是兩邊

- [ ] **④ 測「那一行」,不是測 helper** —— 為 helper 寫再多髒值斷言,
      都不會覆蓋到模組層那一行 / 寫在 `main()` 行內的規則。
      **判準:把修改逐項還原,測試會不會 FAIL?** 不會 FAIL 的就是沒有覆蓋。
- [ ] **⑤ 陽性對照(兩格,缺一不可)** ——
      (a) 該擋的有擋下;(b) **該放行的仍然放行**。

- [ ] **⑥ 派獨立驗證,而且不是一輪** —— 見下節:四輪,每輪各打掉一個**新造的**同族缺陷。

- [ ] **⑧ 不要發明新的分類。** 修 fail-open 時最容易做的事,是替某些失敗開一個

      不影響判斷」,而那條候選對它的真相關是 ~1.0)。

- [ ] **⑨ 新加的告警,先算它多久叫一次。** 一個在**常態**下會響的告警等於沒有告警

- [ ] **⑩ 註解裡的全稱句要當程式碼驗。** 「A 是 B 的補集」「X 必然 Y」寫下去之前,
