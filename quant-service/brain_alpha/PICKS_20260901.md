理由是今天實測出來的兩個數字：

   （我一開始的假設是「同一個 `group_rank(ts_rank(...))` 骨架套誰都會撞」，量完被推翻。）

   self-corr 0.77~0.90 全被擋，結論會是「今天沒有安全的候選」——而同一個庫存裡
   analyst4 / option9 / pv13 有交得出去的躺著沒被看到。

   **集中度實測（2026-09-01 22:05，兩種算法都列）：**

   | 算法 | 通過總數 | fundamental2 | 佔比 |
   |---|---|---|---|
   | 唯一 key（`expr`+`settings` 去重） | 572 | 475 | **83.0%** |
   | 照 `alpha_id` 去重 | 479 | 382 | **79.7%** |

   🔴 **更正：我先前寫的「1,220 條裡 1,154 條 = 94.6%」是錯的算法。**
   那是數帳本的**行數**，而帳本有重複行——今天早上抓到 9 個挖礦程序疊在一起跑，
   同一個 `key` 被不同程序各跑一次各寫一行。重複倍率**每個資料集不一樣**：


   fundamental2 排在舊掃描順序的最前面，所以被疊跑最多次、被灌水最嚴重。
   結果就是**我用來證明「集中度太高」的那個數字，本身被同一個 bug 灌大了**

   > 督導的假設是「94.6% 是 08-29 寫進 memory 的快照、之後帳本長大了」——
   > **假設不成立**。那個數字是今天早上 10:35 我自己算的，分母 1,220 是當時的行數

   > memory 要改的是同一件事，但理由要寫對，否則下一個 session 會以為
   > 「數字會隨時間漂」而不是「那個算法本來就不能用」。

`records` 拿不到時 `done` 是 `None` 而不是 0，板子印
**「⚠️ 查不到已交幾條（不是 0，是問不到）」**。餵假 401 驗過。

漏交和重複提交的處置完全相反，所以這兩件事必須分得出來。
